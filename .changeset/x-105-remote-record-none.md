X-105: `metistry remote` — how the owner's phone reaches this Mac (plan §2.23, M20): the record, the adapter interface, and None. `deployment.yaml` gains a `remote:` block — `provider` (none | tailscale | relay | cloudflare | zrok | ngrok | port-forward), `mode`, the `origin` it yields and non-secret `settings` — strict in core's schema, the instance's block winning whole over the seed's, never a credential. `metistry remote [status] | set | authorize | test | off` with `--json`, `--dry-run`, `--instance`: `set` previews without `--yes`; with it, the new provider is configured first, its origin must answer from this Mac, the record is written through the protected write, and only then is the old provider revoked — a failed configure writes nothing, an origin that never answers writes and revokes nothing. A token is read on stdin or hidden at a prompt (the `secrets set` reader, now `stdin-value.ts`); a value in argv is refused and not echoed. `metistry up` derives `METISTRY_ORIGIN` from the record — the remote origin first, the loopback origin second; with None, loopback only — and drops a hand-written remote origin, saying so. The `RemoteProvider` interface (`detect`, `configure`, `status`, `revoke`, optional `authorize`) and its registry live in `packages/cli/src/remote/`; this release ships **None**, whose doctor row is `ok`. Doctor's `remote` kind gives every provider *tool present*, *proxy listener* — **`failed` when the recorded upstream is the console's main port** — and *answers from this Mac*. `docs/ops/remote-access.md` is new.
